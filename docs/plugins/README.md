# Plugin Architecture

Plugins are how AICOMPANY-OS scales to hundreds of agents and integrations **without** widening the trusted
core. The design goal: *a malicious or buggy plugin can, at worst, fail its own capabilities.*

## 1. Threat model

| Threat | Control |
|---|---|
| Malicious code shipped in a plugin | Integrity map over **every** file + Ed25519 signature; unsigned ⇒ COMMUNITY tier ⇒ container isolation mandatory |
| Code swapped after review (TOCTOU) | Approved manifest digest pinned; integrity + digest re-verified at every activation |
| Capability creep at runtime | Object-capability `PluginContext`; every call checks the grant; violations audited, alerted, and auto-suspend after N |
| Forged platform events (`ApprovalGranted`) | Plugins may publish only `<Namespace>.<Event>` |
| Hijacking core agents/actions | Agent ids must be `<plugin>-*`, actions `<plugin_module>.*`; core actions cannot be overridden or unregistered |
| Privilege escalation via agent specs | Agent permissions ⊆ manifest declaration, never in the forbidden set; reviewers see them in the install proposal |
| Weakening security policy | `policy_guard` plugins require CORE tier and are wrapped *restrict-only* (ALLOW ignored, exceptions ⇒ REQUIRE_APPROVAL) |
| Data exfiltration | `net:egress:<exact-host>` only, HTTPS only, no redirects; container plugins egress via Squid allow-list |
| Secret harvesting | `secrets:read:<prefix>` with path-traversal checks; every read audited |
| Cross-tenant leakage | Handlers drop events and refuse actions from other tenants |
| Runaway / buggy plugin | Per-call timeout; error budget ⇒ auto-SUSPEND with full registration rollback |
| Module shadowing (`import requests` → plugin file) | Top-level module must equal plugin name; resolved file must live under the plugin dir; collisions refused |

## 2. Package layout

```
my-plugin/
├── plugin.yaml          # manifest (schema below)
├── plugin.sig           # "<key-id>:<base64 ed25519 signature>" (optional; absent ⇒ COMMUNITY)
└── my_plugin/           # top-level module MUST equal name with '-' → '_'
    ├── __init__.py
    └── plugin.py        # entrypoint class
```

## 3. Manifest (`aicos.io/v1`)

```yaml
api_version: aicos.io/v1
name: hubspot-sync                 # ^[a-z][a-z0-9-]{2,49}$
namespace: HubSpot                 # event namespace; publish only HubSpot.*
version: 0.1.0                     # semver
publisher: aicompany-os            # must match the signing key's publisher (VERIFIED tier)
kinds: [action, event_subscriber, agent]   # agent | action | llm_provider | knowledge_loader | event_subscriber | policy_guard
entrypoint: hubspot_sync.plugin:HubSpotSyncPlugin
aicos_version: ">=0.1.0,<0.2.0"
isolation: in_process              # in_process (CORE/VERIFIED only) | container
capabilities:
  - events:subscribe:LeadFound
  - events:publish:HubSpot.ContactQueued
  - actions:register:hubspot_sync.upsert_contact
  - net:egress:api.hubapi.com      # SENSITIVE
  - secrets:read:plugins/hubspot   # SENSITIVE
  - agents:register
actions:
  - { action: hubspot_sync.upsert_contact, permission: crm:write }
agents:
  - id: hubspot-sync-enricher
    department: sales
    permissions: [task:read, knowledge:read, crm:write]
    tools: [hubspot_sync.upsert_contact]
resources: { cpus: 0.25, memory_mb: 256, timeout_s: 20 }
dependencies: []
integrity: { "hubspot_sync/plugin.py": "<sha256>", ... }   # generated by `aicos-plugin hash`
```

### Capability grammar

| Capability | Grants | Sensitive |
|---|---|---|
| `events:subscribe:<Type>` / `events:subscribe:*` | receive events | `*` = yes |
| `events:publish:<Namespace>.<Event>` | publish namespaced events | |
| `llm:invoke:<task>` / `llm:invoke:*` | call the router (local models by default) | |
| `memory:read:<company\|project\|agent>` | semantic recall | |
| `memory:write:<scope>` | write memory | `company` = yes |
| `knowledge:read` / `knowledge:ingest` | knowledge base | |
| `net:egress:<host>` | HTTPS to exactly that host | **yes** |
| `secrets:read:<prefix>` | secrets under prefix | **yes** |
| `actions:register:<action>` | contribute a governed action | yes if bound to a critical permission |
| `agents:register` · `models:register` · `loaders:register` | contribute agents / LLM providers / loaders | `models:register` = yes |

Sensitive capabilities are listed separately in the install proposal so reviewers can't miss them.

## 4. Trust tiers & isolation

| Tier | How obtained | Allowed isolation | Extra powers |
|---|---|---|---|
| CORE | signed by a project release key in `security/trusted-keys` | in_process, container | `policy_guard` |
| VERIFIED | signed by an allow-listed publisher key (publisher must match) | in_process, container | — |
| COMMUNITY | unsigned or unknown signer | **container only** (gVisor profile) | — |

A signature that is present but **invalid** is treated as tampering: verification fails (it does not
downgrade to COMMUNITY).

> **Honest limitation:** in-process Python cannot be sandboxed. For CORE/VERIFIED plugins the capability
> facade is a *policy* boundary backed by code review + signatures. The *security* boundary for untrusted
> code is the container runtime (`community-plugin` sandbox profile: `runsc`, no caps, read-only, egress proxy).
> The container runtime speaks the same `PluginContext` API over JSON-RPC (stdio); implement
> `ContainerPluginRuntime` (`start`/`stop`) to plug in your orchestrator (Docker, Kubernetes Jobs, Firecracker).

## 5. Lifecycle

```
discover → verify → request_install ──(approval gateway, HIGH risk, 1 approver, SoD)──► install → activate
                                                                                        ▲         │
                                                                         re-verify ─────┘   suspend/uninstall
```

| Step | API | Who |
|---|---|---|
| discover | `PluginManager.discover(dir)` | platform at boot |
| verify | `POST /v1/plugins/{name}/verify` | `plugin:manage` |
| request install | `POST /v1/plugins/{name}/request-install` | `plugin:install` + MFA → proposal |
| approve | `POST /v1/approvals/{id}/decision` | a *different* Admin with MFA |
| install + activate | `POST /v1/plugins/{name}/install` `{grant_token}` | requester, MFA |
| suspend | `POST /v1/plugins/{name}/suspend` | `plugin:manage` (also automatic) |

Every transition is audited and emits `PluginStateChanged`.

## 6. SDK

```python
from aicos.plugins.sdk import ActionRequest, DomainEvent, Permission, Plugin, PluginContext, PluginRegistrar


class MyPlugin(Plugin):
    def activate(self, ctx: PluginContext, reg: PluginRegistrar) -> None:
        reg.register_action("my_plugin.sync", Permission.CRM_WRITE, self.sync)
        reg.subscribe("LeadFound", self.on_lead)

    async def on_lead(self, e: DomainEvent) -> None:
        await self.ctx.publish("MyPlugin.LeadSeen", {"id": e.id})

    async def sync(self, req: ActionRequest) -> dict:
        token = self.ctx.secret("plugins/my-plugin/token")
        async with self.ctx.http() as client:  # egress-guarded
            r = await client.post("https://api.example.com/sync", json=req.payload, headers={"Authorization": f"Bearer {token}"})
        return {"status": r.status_code}
```

`PluginContext`: `publish`, `complete` (LLM), `recall` / `remember` (memory), `secret`, `http`, `check_egress`, `log`.
`PluginRegistrar`: `register_agent`, `register_action`, `subscribe`, `register_llm_provider`, `register_loader`, `add_policy_guard`.
All registrations are recorded in an undo log and rolled back on failure/suspension.

Actions contributed by plugins are **governed exactly like core actions**: an agent proposes, the policy engine
decides, critical permissions go to the approval queue, and the result is audited.

## 7. Tooling

```bash
aicos-plugin keygen --out security/keys/acme           # Ed25519 keypair (.key 0600)
aicos-plugin hash plugins/examples/hubspot-sync         # regenerate integrity map
aicos-plugin sign plugins/examples/hubspot-sync --key security/keys/acme.key --key-id acme-2026
aicos-plugin validate plugins/examples/hubspot-sync     # schema + integrity + sensitive caps + digest
```

CI (`plugin-integrity` job) validates every bundled plugin. `plugins/examples` is excluded from auto-formatting
because formatting a signed artifact invalidates its integrity map — exactly as intended.

## 8. Health & fail-safe

* Handler timeout: `resources.timeout_s`
* Error budget: `error_threshold` (default 5) ⇒ SUSPENDED
* Capability violations: `violation_threshold` (default 3) ⇒ SUSPENDED + `SecurityAlert`
* Suspension removes every registration atomically; resumption re-verifies integrity and the approved digest.
